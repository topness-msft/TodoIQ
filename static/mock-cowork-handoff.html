Illustrative, not a screenshot. The point is that this card, the parameter display, and the allow/deny gate already exist and are maintained by the Cowork team.
Why this is worth considering. Phase 2B (our own human gate: nonce, draft_hash, execute route, receipt) has been blocked for weeks because no channel passes both gates — Teams PostMessage emits no approval event, and calendar CreateEvent fails after approval. Handing off sidesteps that entirely. We never build an execute route, so “TodoIQ cannot write to M365” stays literally true.
Open question that decides this. Our previews run under the --tool-callback-config write barrier. Nobody has yet tested whether that barrier is client-side per-request (so the web session can execute normally) or sticky on the conversation (so the handed-off session would also refuse to send). If it is sticky, option 1 does not work for execution and the handoff is only good for interactive research. This is one probe and should be run before any build.
Honest limitation either way. Once handed off, TodoIQ has no receipt. It cannot show “sent” without re-reading the conversation later, so the mock says “not tracking the outcome” rather than implying a status it does not have. Polling the conversation for a receipt is a possible follow-up, not something to imply now.
